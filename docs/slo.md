# SLO・アラーム設計と一次対応

サンプルアプリ向けの**仮の SLO** です。実際のサービスではユーザーと合意した値に置き換えます（`slo_availability_target` / `slo_latency_threshold_seconds`）。

## 方針

- アラームは「**ユーザーが困っているか**」だけを鳴らす。CPU・メモリなどの原因系メトリクスはダッシュボードに出すだけで、アラームにしない（閾値超過＝ユーザー影響ではなく、誤報と通知疲れの原因になるため）。
- 例外は **RDS 空き容量** のみ。枯渇するとユーザー影響が急激に深刻化し、SLO アラームでは間に合わないため。
- 通知は緊急度で分ける。`page`（即時対応）と `ticket`（業務時間内に対応）の2つの SNS トピック。

## SLI / SLO

| 項目 | SLI（ALB メトリクスから算出） | SLO（仮） |
| --- | --- | --- |
| 可用性 | 1 − エラー数 / 総リクエスト数。エラー = `HTTPCode_Target_5XX_Count` + `HTTPCode_ELB_5XX_Count`、総数 = `RequestCount` + `HTTPCode_ELB_5XX_Count` | 99.5%（30日） |
| レイテンシ | `TargetResponseTime` の p95 | 500ms 未満 |

- **エラーバジェット**: 30日の可用性 SLO 99.5% なら、リクエストの 0.5% までは失敗してよい。
- ターゲット停止時に ALB が返す 503（`HTTPCode_ELB_5XX_Count`）も、ユーザーから見れば失敗なのでエラーに含める。

## アラーム

### 可用性: エラーバジェット消費率（multi-window multi-burn-rate）

消費率 = エラー率 ÷ (1 − SLO)。1.0 なら 30 日でちょうどバジェットを使い切るペース。長窓と短窓の**両方**が閾値を超えた時だけ通知します（長窓だけだと復旧後も鳴り続け、短窓だけだと一時的な揺れで鳴るため）。

| 複合アラーム | 条件（AND） | 意味 | 通知先 |
| --- | --- | --- | --- |
| `*-slo-availability-fast-burn` | 1時間 ≥ 14.4倍 かつ 5分 ≥ 14.4倍 | バジェットの2%を1時間で消費するペース。今ユーザーがエラーを受けている | page |
| `*-slo-availability-slow-burn` | 6時間 ≥ 6倍 かつ 30分 ≥ 6倍 | バジェットの5%を6時間で消費するペース。放置すると月内に使い切る | ticket |

### レイテンシ

`*-slo-latency-p95`: p95 が閾値を超えた状態が 30 分間（5分窓 6 つ中 5 つ）続いた場合に ticket 通知。

### 原因系の例外

`*-rds-free-storage-low`: RDS 空き容量が割当の 15% 未満。ticket 通知。

### 誤報対策

- 5分あたりの最小リクエスト数（既定 10）未満の窓は評価しない。夜間などの低トラフィック時に数件のエラーで鳴るのを防ぐ。
- データ欠損は `notBreaching`（無トラフィックを異常扱いしない）。

## 簡略化している点（正直なところ）

- レイテンシは「閾値以内のリクエスト比率」ではなく **p95 の閾値比較**で近似している。ALB は閾値以内のリクエスト数を出さないため。厳密にやるならアプリ側でヒストグラムを計測する。
- 低トラフィックでは無トラフィック＝正常扱いになる。外形監視（CloudWatch Synthetics 等）を足せば、トラフィックが無い時の死活も捉えられる。
- 窓の長さ・倍率（14.4 / 6）は Google SRE Workbook の推奨値をそのまま使用。トラフィック特性に合わせた調整が必要。

## 一次対応（runbook）

### fast-burn（page）
1. ダッシュボード（`<project>-<env>`）で「リクエスト数とエラー数」を確認し、`target 5xx` と `elb 5xx` のどちらが多いかを見る。
2. `elb 5xx` 中心 → 正常ターゲット数を確認。0 なら ECS サービスのイベント・タスク停止理由を確認（`aws ecs describe-services`）。
3. `target 5xx` 中心 → CloudWatch Logs `/ecs/<name>` でアプリのエラーを確認。直近のデプロイがあれば**まずロールバック**（前のタスク定義へ戻す）。
4. 依存先（RDS 接続数・CPU）をダッシュボードで確認。
5. 復旧後、ポストモーテムでバジェット消費量を記録。

### slow-burn（ticket）
1. 消費率グラフ（1h 窓）でエラーが常態化していないかを確認。
2. エラーの上位パターンをログから特定し、修正チケット化。バジェット残量が少なければ新機能のリリースを抑制し信頼性改善を優先する。

### latency（ticket）
1. 応答時間グラフとリクエスト数を比較（負荷起因か）。
2. 負荷起因なら ECS タスク数（オートスケール上限 `max_capacity`）と CPU を確認。上限張り付きなら上限引き上げ。
3. 負荷が低いのに遅い場合は RDS（CPU・接続数）と遅いクエリを確認。

### rds-free-storage-low（ticket）
1. `db_allocated_storage` を増やして apply（RDS のストレージ拡張）。
2. 急増していれば、ログ/一時テーブル/不要データの肥大化原因を調査。

## 通知先の設定

`alarm_email` を tfvars に設定すると、`page` / `ticket` 両トピックにメール購読が作られます（初回は確認メールの承認が必要）。本番運用では `page` を PagerDuty / Slack 等のオンコール手段へ繋ぎ替えます。
