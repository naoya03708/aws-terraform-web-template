# 0002. トランクベース開発とタグによる prod 昇格

状態: Accepted

## 背景
dev / prod の2環境を運用する。環境ごとにブランチを持つ（develop / production 等）と、ブランチ間の差分が積み上がり、マージ地獄とレビュー漏れの原因になる。

## 決定
- `main` を唯一の長命ブランチとし、作業は短命ブランチ（1〜2日）から PR → squash merge。
- 未完成の機能はフラグ（例: `enable_waf = false`）で無効のままマージする。
- `main` へのマージで dev に自動 apply（`AUTO_DEPLOY_DEV` で有効化）。prod は**同じコミット**にリリースタグ `vX.Y.Z` を打ち、GitHub Environment の承認を経て apply する。
- prod の apply 前に、タグが `main` 上のコミットであることを検証する。
- `main` はブランチ保護（PR 必須・CI 必須・linear history・force push 禁止）。

## 理由
- 環境間で「何が違うか」はブランチではなく tfvars だけになり、dev で試したものがそのまま prod に昇格する。
- 承認ゲートとタグ検証により、レビューと CI を経ていないコミットが prod に出ない。

## トレードオフ
- フラグ運用の規律が必要（不要になったフラグを残さない）。
- 1人運用のため、承認ゲートは形式的になりがち。チーム運用では必須レビュアーを複数に設定する。
