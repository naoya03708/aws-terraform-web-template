# 0003. アラームは SLO（ユーザー体験）ベースにする

状態: Accepted

## 背景
CPU 80% やメモリ 90% といったリソース閾値のアラームは、ユーザー影響の有無と対応していない。影響が無いのに鳴り（誤報・通知疲れ）、影響があるのに鳴らない（閾値未満で劣化）ことがある。

## 決定
- ユーザー体験を表す SLI（可用性・レイテンシ）から SLO を定義し、アラームは SLO に紐づくものだけにする。
- 可用性はエラーバジェット消費率の multi-window multi-burn-rate で通知（急速消費は page、緩やかな消費は ticket）。
- 原因系メトリクスはダッシュボード表示のみ。唯一の例外は RDS 空き容量（枯渇は SLO アラームでは間に合わないため）。
- SLO はサンプルアプリ用の仮値（可用性 99.5% / p95 500ms）とし、変数で変更可能にする。

## 理由
- 鳴ったら必ずユーザーが影響を受けているので、対応の優先度が明確になる。
- バーンレートにより「どれくらいの速さでバジェットを使っているか」で緊急度を決められる。

## トレードオフ
- ALB メトリクスのみで算出しているため、レイテンシは p95 の閾値比較で近似している。
- 低トラフィックでは評価をスキップするため、無トラフィック時の死活は捉えられない（外形監視で補う余地がある）。
- 詳細は [docs/slo.md](../slo.md)。
